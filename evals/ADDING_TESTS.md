# Как добавить новое требование к сервису

Инструкция для случая, когда вы заметили ошибку в отчёте или хотите
закрепить новое правило, чтобы оно больше не нарушалось.

---

## Принцип

Каждое требование проходит один и тот же путь:

```
заметили проблему
   ↓
① сформулировали как проверяемое утверждение
   ↓
② определили слой (расчёт / логика / текст)
   ↓
③ записали eval в evals.json
   ↓
④ добавили проверку в код (если слой 1 или 2)
   ↓
⑤ прогнали — новый тест падает
   ↓
⑥ починили код — тест проходит
```

Пункт ⑤ важен. Если новый тест сразу зелёный — вы, скорее всего, проверяете
не то, что думаете.

---

## Шаг 1. Сформулировать как проверяемое утверждение

Требование должно быть таким, чтобы на него можно было ответить «да» или
«нет», глядя на конкретное число или строку.

| Плохо | Хорошо |
|-------|--------|
| «Отчёт должен быть точным» | «Сумма бинду по 12 домам равна 337» |
| «Текст должен быть понятным» | «В тексте нет джйотиш-терминов вне тега `<span class="jy">`» |
| «Не путать даши» | «Текущая МД для Анны на 2026 год = Раху» |
| «Учитывать ретроградность» | «Сатурн помечен как ретроградный в поле `retrograde`» |

Если сформулировать не получается — требование пока не готово к тому,
чтобы становиться тестом. Уточните его.

---

## Шаг 2. Определить слой

| Слой | Что проверяет | Вес | Порог | Куда добавлять код |
|------|---------------|-----|-------|--------------------|
| **1 — расчёт** | Числа из эфемерид: позиции, даши, бинду | 50% | 90% | `verify_chart.py` или отдельный модуль |
| **2 — логика** | Выводы следуют из чисел: АК, йоги, ранги | 30% | 80% | `verify_chart.py` |
| **3 — текст** | Нарратив не противоречит числам | 20% | 85% | проверка готового HTML |

Правило выбора: если для проверки нужны только числа — это слой 1.
Если нужно сопоставить числа между собой — слой 2. Если нужно читать
текст отчёта — слой 3.

---

## Шаг 3. Записать eval

Открыть `evals.json`, добавить объект в массив `evals`. Взять следующий
свободный `id`.

```json
{
  "id": 13,
  "name": "короткое_имя_латиницей",
  "category": "layer_1_calculation",
  "description": "Одна строка: что именно проверяется",
  "prompt": "Запрос, на котором это проявляется",
  "ground_truth": {
    "поле": "ожидаемое значение",
    "source": "откуда взят эталон — pyswisseph / классика / внешний сайт"
  },
  "expected_output": "Что должно получиться",
  "expectations": [
    "Утверждение 1 — проверяемое",
    "Утверждение 2 — проверяемое"
  ],
  "common_errors": [
    "Как это ломается на практике и почему"
  ]
}
```

**Поле `common_errors` не декоративное.** Оно объясняет будущему читателю
(или Claude Code), какую именно ошибку тест ловит. Без него через полгода
непонятно, зачем тест нужен.

---

## Шаг 4. Добавить проверку в код

### Для слоёв 1 и 2

Проверки живут в функции `verify_against_ground_truth()` в `verify_chart.py`.
Каждая добавляет словарь в список `checks`:

```python
# Новая проверка
gt_value = ground_truth.get('моё_поле')
if gt_value:
    actual = chart['путь']['к']['значению']
    checks.append({
        'check': f'Читаемое описание: ожидается {gt_value}',
        'passed': actual == gt_value,
        'evidence': f'Рассчитано: {actual}',
    })
```

Три поля обязательны:
- `check` — что проверяли, человеческим языком
- `passed` — `True` / `False`
- `evidence` — что получилось на самом деле; выводится только при провале,
  поэтому должно быть достаточно информативным, чтобы понять причину

Обёртка `if gt_value:` нужна, чтобы проверка молча пропускалась для тех
eval-ов, где это поле не задано.

### Если нужен новый расчёт

Не пихать в `verify_chart.py`. Создать отдельный модуль по образцу
`ashtakavarga.py`:

```python
# my_module.py

def validate_tables():
    """Самопроверка констант. Вызывается при импорте."""
    ...

_ok, _errs = validate_tables()
if not _ok:
    raise MyModuleError("Константы повреждены:\n  " + "\n  ".join(_errs))

def compute_something(...) -> dict:
    result = ...
    # Обязательно: внутренняя валидация результата
    if not внутренняя_проверка(result):
        raise MyModuleError("Контрольная сумма не сошлась")
    return result
```

Два правила для новых модулей:
1. **Самопроверка при импорте.** Повреждённые константы должны ронять
   импорт, а не портить чужой отчёт молча.
2. **Контрольная сумма, если она существует.** В джйотише многие величины
   имеют фиксированные инварианты (САВ = 337, сумма Вимшоттари = 120 лет,
   сумма градусов навамши = 30). Использовать их.

### Для слоя 3 (текст)

Проверки работают по готовому HTML. Формат — списки обязательных и
запрещённых утверждений:

```json
"ground_truth": {
  "required_narrative_facts": [
    {"claim": "Текущая МД — Раху", "source": "vimshottari"}
  ],
  "forbidden_narrative_facts": [
    {"claim": "Текущая МД — Меркурий", "error": "неверная позиция Луны"}
  ]
}
```

Проверка — поиск подстрок или регулярок в готовом файле:

```python
html = open(output_file, encoding='utf-8').read()
for item in gt['forbidden_narrative_facts']:
    checks.append({
        'check': f"Текст НЕ содержит: {item['claim']}",
        'passed': item['claim'].lower() not in html.lower(),
        'evidence': item['error'],
    })
```

---

## Шаг 5. Прогнать и убедиться, что тест падает

```bash
python verify_chart.py run-all --evals evals.json
```

Новый тест должен **упасть**. Если он сразу прошёл — либо код уже
удовлетворяет требованию (тогда это регрессионный тест, и это нормально,
но проверьте формулировку), либо проверка написана так, что всегда истинна.

Быстрая проверка на «всегда истинную» проверку: временно поменяйте
ожидаемое значение на заведомо неверное и убедитесь, что тест краснеет.

---

## Шаг 6. Починить и закрепить

После исправления:

```bash
python verify_chart.py run-all --evals evals.json   # всё зелёное
```

Обновить в `README.md` таблицу «Известные источники ошибок» — добавить
строку с новой ошибкой, её причиной и защитой.

## Реальный пример: как появилась проверка бинду

**① Заметили.** В альманахе Анны бинду 10-го дома стояло 32.
Пересчёт дал 38. Проверили остальные — расхождения до 10 баллов.

**② Слой.** Числа из формулы, никакого текста — **слой 1**.

**③ Eval.** Записали два: `#11 ashtakavarga_checksums` (инвариант 337 для
любой карты) и `#12 ashtakavarga_anna_reference` (конкретные 12 чисел Анны).

**④ Код.** Алгоритм новый → отдельный модуль `ashtakavarga.py` с
самопроверкой таблиц при импорте и валидацией результата. В
`verify_chart.py` добавили четыре проверки: сумма САВ, суммы БАВ,
совпадение с эталоном, сильнейший дом.

**⑤ Прогон.** До внедрения проверок вообще не было — тестов на бинду
не существовало, поэтому «падение» здесь означало отсутствие покрытия.

**⑥ Результат.** Было 17 проверок, стало 21. Оба выпущенных альманаха
пересчитаны, два неверно обоснованных вывода исправлены.

Что важно: ошибка существовала в двух выпущенных документах и не была
заметна, потому что числа выглядели правдоподобно. Поймал её не глаз,
а контрольная сумма.

## Что стоит покрыть следующим

Кандидаты, где есть проверяемые инварианты:

| Требование | Слой | Инвариант для проверки |
|---|---|---|
| Вимшопака-балл считается, а не оценивается | 1 | Веса 16 варг в сумме дают 20 |
| Навамша D9 рассчитывается алгоритмически | 1 | 9 навамш × 3°20′ = 30° |
| Йога объявлена только если условия выполнены | 2 | Каждая йога → предикат на позициях |
| Все термины в отчёте обёрнуты в `<span class="jy">` | 3 | Регулярка по списку терминов |
| В отчёте нет дома с бинду вне 18–42 | 1 | Границы диапазона |
| Сумма всех МД Вимшоттари = 120 лет | 1 | Инвариант системы |

Вимшопака — самый приоритетный: сейчас баллы в альманахах проставлены
оценочно, ровно как были бинду до этого исправления.

## Второй реальный пример: Вимшопака и находка про D60

**① Заметили.** Вимшопака-баллы в альманахах стояли оценочно, ровно как
бинду до этого. Инвариант известен: веса 16 варг дают ровно 20.

**② Слой.** Числа из формулы — **слой 1**.

**③ Eval.** `#13 vimshopaka_weights` (инвариант 20 для любой карты)
и `#14 vimshopaka_anna_reference` (конкретные баллы Анны).

**④ Код.** Модуль `vimshopaka.py`: расчёт всех 16 варг, таблица
достоинств, самопроверка при импорте.

**⑤ Прогон — и здесь тест упал не там, где ожидалось.** Эталон был
записан по округлённым градусам (Марс 28.50°), а реальная позиция —
28.4977°. Деление D60 идёт по 0°30′, граница ровно на 28.5000°.
Три угловых секунды переворачивают D60 из Льва в Рак, а для Марса
Рак — падение. Вес D60 самый большой из шестнадцати (4.0), поэтому
балл упал с 13.00 до 11.43 и Марс потерял первое место.

**⑥ Результат.** Помимо исправления эталона появилась новая функция
`analyse_sensitivity()`: она проверяет, не стоит ли планета вплотную
к границе деления варги, и показывает, насколько сдвинется балл при
пересечении. Для Анны нашлось 4 таких позиции, максимальный сдвиг 1.8
балла; для Гилберта — 6 позиций, сдвиг до 1.4.

**Вывод, который стоит запомнить.** Тест, упавший по неожиданной
причине, ценнее теста, упавшего по ожидаемой. Здесь он вскрыл не ошибку
в коде, а свойство самой методики: при неточном времени рождения
Вимшопака-балл недостоверен в пределах ±1.5–2 пунктов, и об этом надо
писать в отчёте, а не делать вид, что число точное.

## Правило про округление в эталонах

Не записывайте ground_truth по округлённым входным данным. Всегда берите
значения из фактического прогона:

```bash
python verify_chart.py calculate --date ... --time ... --quiet > truth.json
```

Округление до сотых в градусах кажется безобидным, но деления варг идут
шагами от 0°30′ (D60) до 0°40′ (D45), и на границе округление меняет знак.
